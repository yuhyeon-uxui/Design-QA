# UX 의사결정 기록 (UX Decisions)

이 문서는 프로젝트를 진행하며 발생한 주요 이슈와, 이를 해결하기 위한 UX적 의사결정(Trade-off 및 솔루션) 과정을 기록합니다.

---

## 1. 개발자 협업을 위한 피그마-실제화면 비교 뷰 도입

### 🤔 배경 및 문제 제기 (개발자 실무 피드백)
- 프론트엔드 개발자가 디자인 QA를 처리할 때는 단순히 "텍스트로 된 수정 요청사항"만 보고 작업하는 것이 불가능합니다.
- 실무에서는 **"피그마 화면(CSS 수치 확인용)"**과 **"실제 테스트 앱 화면"**을 직접 비교하고, 차이가 있으면 코드를 수정하는 방식으로 작업합니다.
- 만약 QA 보드가 '캡처 이미지'만 덩그러니 제공한다면, 개발자는 정확한 수치를 찾기 위해 결국 피그마를 다시 열고 해당 화면을 직접 검색해야 하는 큰 번거로움(Context Switching)이 발생합니다. 이로 인해 "차라리 피그마에 댓글을 남기는 게 실무적으로는 편하다"는 피드백이 제기되었습니다.

### 💡 해결 방안 (UX 솔루션 적용)
단순히 피그마 댓글 기능으로 돌아갈 경우, 기획/QA팀 관점에서의 진행률 트래킹, 엑셀 추출, 상태 관리가 불가능해집니다. 따라서 Design QA Hub 내에서 개발자의 니즈를 충족시키는 방향으로 UX를 개선하기로 결정했습니다.

1. **스플릿 뷰 (Side-by-Side Comparison)**
   - 가장 핵심 화면인 'QA 보드'의 좌측 이미지 영역을 분할하여, **[피그마 시안 이미지]**와 **[실제 구현 캡처 이미지(핀 표기)]**를 나란히 띄워줍니다.
   - 이를 통해 개발자는 듀얼 모니터 없이도 한 화면에서 "시안과 구현의 차이"를 즉각적으로 비교할 수 있습니다.

2. **피그마 프레임 딥링크 (Deep Link to Figma)**
   - 단순히 프로젝트 전체 피그마 주소만 두는 것이 아니라, 이슈 폼 내부에 **해당 화면의 특정 피그마 프레임(Node ID)으로 바로가는 버튼**을 큼직하게 배치합니다.
   - 개발자가 픽셀 수치를 봐야 할 때 클릭 한 번으로 피그마 Inspect 뷰로 직행하도록 돕습니다.

### 🚀 향후 고도화 예정 사항
- **오버레이 슬라이더 (Opacity Diff)**: 두 이미지를 겹쳐두고 투명도를 조절하는 슬라이더를 제공하여, 1~2px 어긋난 마진/패딩을 시각적으로 명확히 잡아낼 수 있는 기능.
- **Figma Plugin 개발**: QA 보드에서 등록된 이슈 핀을 피그마 플러그인을 통해 피그마 캔버스 위에 실시간 동기화하여 보여주는 궁극적인 협업 환경 구축.

## 2. QA 진행률 표기 정책 (Progress Calculation)

### 🤔 고민 배경
- **화면 기준 계산의 한계:** 총 2장의 화면 중 1장은 '완료', 1장은 핀이 100개 찍힌 '미완료' 상태일 때 50%로 표기되면 이슈의 리스크(핀 개수)가 묻히는 문제.
- **핀 기준 계산의 한계:** 완벽하게 디자인되어 수정할 곳이 없는 화면은 핀이 0개이므로, 화면 검수라는 수고로움이 진행률(0%)에 전혀 반영되지 않는 모순 발생.

### 💡 결정된 정책: 하이브리드 점수 방식 (Hybrid Score)
- **화면 검수**와 **이슈 해결**을 모두 각각의 독립된 '태스크'로 인정하고 합산하여 계산합니다.
- **계산식:** `(완료된 화면 장수 + 완료된 핀 수) / (전체 화면 장수 + 전체 핀 수) * 100`
- **효과:** 완벽하게 통과된 화면의 수고로움도 인정하면서, 이슈(핀)가 많은 화면의 리스크도 동시에 반영하여 대시보드와 QA 보드의 진행률 수치를 100% 동일하게 동기화했습니다.

## 3. 미작성 화면 이탈 방지 정책 (Exit Warning Policy)

### 🤔 고민 배경
- QA 보드에서 모든 화면을 확인하지 않고 대시보드로 돌아가려 할 때 어떻게 처리할 것인가?
- **초기 방안:** "머무르기"와 "나가기" 선택지를 주어 유저의 통제권(퇴근 등)을 보장. (Soft Warning)
- **동료 협의 결과:** QA 누락을 원천 차단하기 위해 **강제로 모든 화면을 작성(혹은 삭제)해야만 나갈 수 있도록 막자(Hard Block)**는 결론 도달.

### 💡 결정된 정책: 이슈 기반 QA (Issue-Driven QA) 최적화 가이드 이동
- 속도가 빠르고 애자일한 조직의 특성을 반영하여 **'문제가 발생한 화면만 리포팅하는 이슈 기반 QA'** 방식으로 정책 확정.
- 완벽한 화면(문제가 없는 화면)은 QA 보드에 등록조차 하지 않는 것을 원칙으로 하며, 이에 따라 `[QA 통과]` 등의 상태값은 배제.
- **방어막 플로우 (가이드 이동 방식):**
  1. 사용자가 `< (뒤로 가기)` 버튼 클릭 시, 미작성 케이스를 감지하여 1버튼 알럿 팝업 노출.
  2. **방어 케이스 1 (빈 화면):** 이미지를 아예 올리지 않았거나 핀이 0개인 경우
     - 팝업 내용: *"아직 확인 대기 중인 화면이 남아있습니다. QA를 모두 완료해야 나갈 수 있습니다."*
     - 액션: `[다음 미작성 화면으로 이동]` 버튼 클릭 시 해당 화면으로 자동 이동.
  3. **방어 케이스 2 (빈 핀):** 이미지는 올리고 핀도 찍었으나, 내용(문제점/요청사항)을 한 글자도 적지 않은 핀이 존재하는 경우
     - 팝업 내용: *"이미지는 업로드되었으나 내용이 비어있는 핀(이슈)이 있습니다. 내용을 작성하거나 불필요한 핀을 삭제해주세요."*
     - 액션: `[해당 핀으로 이동]` 버튼 클릭 시, 해당 화면으로 이동함과 동시에 내용이 빈 핀이 자동으로 포커싱 됨.
- **효과:** 미작성된 화면이나 내용이 누락된 핀이 여러 개 남았더라도 팝업 버튼만 누르면서 '도장 깨기' 하듯 자연스럽게 남은 업무를 100% 클리어하도록 부드럽게 강제(Nudge)할 수 있습니다. 완벽한 화면은 유저가 직접 삭제하도록 유도하여 DB 낭비도 막습니다.

## 4. 프로젝트 완료 정책 (Project Completion Policy)

### 🤔 고민 배경
- 사용자가 프로젝트 설정에서 상태를 '완료됨'으로 변경할 때, 해결되지 않은 잔여 이슈가 있는 경우 이를 시스템이 어떻게 제어할 것인가?
- **옵션 A (Strict Block):** 잔여 이슈가 1건이라도 있으면 아예 완료 처리를 불가능하게 강제 방어.
- **옵션 B (Soft Warning):** 잔여 이슈가 있더라도 완료 처리는 허용하되, 사전에 경고 팝업을 제공하여 인지시킴.

### 💡 결정된 정책: 유연한 경고 후 허용 (Soft Warning)
- 실무에서는 급한 배포 일정 등으로 인해 크리티컬하지 않은 이슈(Known Issue)를 안고 가거나 다음 스프린트로 이관한 뒤 QA를 종료해야 하는 현실적인 상황이 존재합니다.
- 따라서 시스템이 엄격하게 막아버리기보다는, 작업자에게 한 번 더 상기시키는 방향으로 유연함을 제공하기로 결정했습니다.
- **플로우:**
  1. 프로젝트 설정에서 상태를 `[완료됨]`으로 선택하고 `[저장하기]` 클릭.
  2. 시스템이 전체 화면을 스캔하여 해결되지 않은 잔여 이슈(누락된 빈 화면 포함) 개수를 파악.
  3. 잔여 이슈가 1건 이상 존재할 경우, 즉시 팝업 노출: *"아직 해결되지 않은 이슈가 남아있습니다. 이대로 QA를 종료하고 완료 처리하시겠습니까?"*
  4. 사용자가 `[확인]`을 누르면 그때 프로젝트가 완료 상태로 덮어씌워지며 변경됨.

## 5. 코멘트 멘션(@태그) 입력창 UX 정책 (Mention Input UI/UX)

### 🤔 고민 배경
- 사용자가 코멘트 입력창에서 `@안유현 대리` 와 같이 사람을 태그할 때, 슬랙(Slack)처럼 입력 필드 내에서 즉시 파란색 '라벨(Pill) UI'로 변환되기를 기대하는 니즈가 발생.
- 멘션 팝업 목록이 뜬 상태에서 키보드 `Enter`를 쳤을 때, 사람 이름이 자동 완성(선택)되지 않고 작성 중인 텍스트 그대로 코멘트가 전송되어버리는 사용성 문제 발견.

### 💡 결정된 정책: 시각적 피드백 타협 및 키보드 자동완성 우선 적용

1. **입력창 내 라벨 UI (시각적 피드백)**
   - 일반적인 `<input>` 태그 구조에서는 특정 단어만 라벨 UI로 부분 스타일링하는 것이 기술적으로 불가함. 이를 구현하려면 꽤 무거운 리치 텍스트 에디터(Rich Text Editor) 라이브러리를 도입해야 함.
   - **결정:** 1차 버전에서는 안정성과 가벼움을 위해 깃허브(GitHub) 방식처럼 **입력 중에는 평문(Plain Text)으로 유지**하고, 전송이 완료되어 **코멘트 목록에 렌더링될 때만 파란색 라벨 UI로 강조하여 보여주기로 타협(옵션 B).** (향후 2차 고도화 시 슬랙 방식의 에디터 도입 검토)

2. **팝업 내 Enter 키 자동완성 동작 (키보드 내비게이션)**
   - 팝업이 떠 있을 때의 `Enter` 키와 평소 코멘트 전송용 `Enter` 키의 동작(Action)을 완벽하게 분리.
   - **결정:** 멘션 팝업이 켜져 있을 때 `Enter` 키 입력 시 코멘트 전송을 차단(Block)하고, 팝업 목록 상단의 유저 닉네임을 **입력창에 텍스트로 자동 완성한 뒤 팝업만 닫도록 개선.**
   - 향후 키보드 위/아래 화살표(↑, ↓) 내비게이션 기능을 함께 보강하여, 마우스 개입 없이 100% 키보드만으로 태그가 가능하도록 UX 완성도를 끌어올릴 예정.

## 6. 통합 및 프로젝트 내 검색 기능 UX 시나리오 (Search UX Scenario)

### 🤔 고민 배경
- 대시보드에 프로젝트가 쌓이거나, 한 프로젝트 내에 리뷰할 화면/핀이 많아질 경우 원하는 이슈를 다시 찾아보는 데 큰 어려움이 예상됨.
- 작성자 이름, 코멘트 내용, 문제점 설명 등 특정 키워드를 기반으로 빠르게 이슈를 추적할 수 있는 기능이 필수적임.

### 💡 결정된 정책: 2-Track 검색 시스템 도입
데이터의 범위에 따라 사용자의 목적이 다르므로, 두 가지 형태의 검색 기능을 분리하여 제공하기로 결정했습니다.

#### 1. 대시보드 통합 검색 (Global Search)
- **목적:** '어느 프로젝트에 있던 이슈인지' 정확히 기억나지 않을 때, 전체 데이터를 관통하여 찾아내는 목적.
- **동작 방식:** 대시보드 상단에 위치. 검색어 입력 시 하위의 모든 `project_screens` 데이터를 로드하여 프로젝트 이름, 핀 설명, 코멘트 내용, 작성자를 모두 스캔.
- **검색 결과 뷰:** 검색 결과를 클릭하면 해당 프로젝트의 특정 화면(스크린)으로 즉시 라우팅.
- **(MVP 한정) UX 타협점:** 현재 구조상 모든 프로젝트의 데이터를 한 번에 가져와야 하므로 데이터 방대화 시 로딩 이슈가 생길 수 있으나, 초기 규모에서는 클라이언트 단 전체 검색(MVP)으로 처리 후 속도 저하 시 서버사이드 인덱싱 도입을 고려.

#### 2. 프로젝트 내부 화면 검색 (In-Project Search)
- **목적:** 특정 프로젝트/화면 내부에서 진행 중인 많은 이슈 중 원하는 조건(텍스트, 상태 등)의 핀만 빠르게 추려내는 목적.
- **동작 방식:** 화면 우측 패널(문의 및 코멘트 영역)에 검색바 배치. 현재 활성화된 화면(`activeDeviceState.pins`) 내부의 이슈만 필터링.
- **결과 하이라이팅:** 검색어와 일치하는 핀만 화면에 표시하거나, 일치하지 않는 핀은 투명도를 크게 낮춰(Dim 처리) 원하는 이슈를 캔버스 위에서 시각적으로 바로 찾아낼 수 있도록 돕는 UX 제공.
